# alint plugin contract (WIT draft)

`alint-plugin/v0.1/plugin.wit` is the draft `alint:plugin@0.1.0` contract:
shared std-only types, an `adapter` world, and an `analyzer` world. Inputs are
host-pushed; there are no host callbacks, resources, handles, or recursive
types in this version. `wire.lock` is the protobuf wire-number map generated by
witforge. It becomes append-only when the contract is released; while 0.1 is a
draft it is regenerated in place (below).

The WIT is the source of truth for the contract. The hand-written traits in
`alint_core::plugin_api` remain the executable v0.21 contract until the
generated `alint-plugin-api` crate replaces them (slice P2). Until then, the
tests in `crates/alint-witforge-consumer` convert every type and trait that
`plugin_api` and the generated code share, account for every item on both
sides, and pair each world with the `plugin_api` trait that implements it, and
`ci/scripts/witforge-consumer.sh` checks the generated code against the WIT, so
a change to either side must update the other in the same pull request.

## Status: draft

0.1 is a draft with no compatibility promise and may still change in place.
The first alint release that loads plugins freezes it: that release adds
`alint-plugin/released`, after which a released version never changes and
changes ship as a new minor version
([ADR-0027](../docs/adr/0027-plugin-contract-0-1-stays-a-draft.md),
`docs/design/plugin-architecture.md` section 8.3).

## Checking and regenerating

`crates/alint-witforge-consumer` holds witforge's output for this contract:
the plain Rust types and traits (`src/plain`), the protobuf schema
(`proto/v0.proto`), and the glue between them (`src/glue`). Its `build.rs`
generates the prost and proto3-JSON code from the schema, so none of that is
committed. The committed files are witforge's output byte for byte, which is
why `src/lib.rs` keeps them out of rustfmt with `#[rustfmt::skip]`.

The committed output is generated with one witforge release, pinned in the
script (`ci/scripts/witforge-consumer.sh --print-version` prints it), and the
script refuses any other version. Install that release from crates.io:

```sh
cargo install witforge-cli --version "$(ci/scripts/witforge-consumer.sh --print-version)" --locked
```

Then check the contract and the committed output:

```sh
ci/scripts/witforge-consumer.sh            # witforge on PATH
WITFORGE_BIN=/path/to/witforge ci/scripts/witforge-consumer.sh
```

After changing `plugin.wit`, update its wire lock, then regenerate the
committed output instead of editing it. While 0.1 is a draft, update the lock
with `witforge lock --first wit/alint-plugin/v0.1`: every entry is a draft, so
a changed member keeps its number with its new type and a removed member's
entry is dropped. (Plain `witforge lock` treats every entry as released: it
refuses a changed type and reserves a removed member's number, which is what a
frozen version needs.)

```sh
ci/scripts/witforge-consumer.sh --write
```

`ci/scripts/test-witforge-consumer.sh` runs the check's controls: the
unmodified tree must pass, also with a relative `WITFORGE_BIN` from another
directory; a changed, extra, or missing generated file, a WIT edit the
committed output does not reflect, an unlocked member, a version directory the
script does not check, or a witforge other than the pinned release must fail;
and `--write` must restore a changed file. Without witforge the controls skip
(exit 77, which `ci/scripts/shell-tests.sh` reports as skipped), unless
`WITFORGE_REQUIRED=1`.

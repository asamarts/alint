# Case study: `dotnet/runtime`

> Marketing/positioning writeup at https://alint.org/examples/dotnet-runtime/. This README is the engineering reference: tooling inventory, mapping, gap catalogue, validation status.

Inventory of the structural-validation tooling in `dotnet/runtime`
and an alint config that replaces the rules alint can express today,
plus a catalogue of the rules that need new alint primitives.

**Repo state captured:** 2026-05-06, sparse-clone of `dotnet/runtime`
at HEAD (main branch). Heaviest test-and-AOT directories excluded
(`/src/tests`, `/src/coreclr/tools/aot`, `/src/installer/pkg`); per-
language top-level dirs and the `eng/`, `.github/`, `.config/`,
`.devcontainer/` subtrees kept in full.

---

## Summary

`dotnet/runtime` is Microsoft's CLR + Mono + NativeAOT runtime, the
BCL (Base Class Library: every `System.*` and
`Microsoft.Extensions.*`), the per-OS native libs, and the cross-arch
installer. Built on the **MSBuild + Arcade SDK** stack
(`Microsoft.DotNet.Arcade.Sdk`, pinned in `global.json::msbuild-sdks`),
with the actual build matrix orchestrated from **186 yml files under
`eng/pipelines/`** (Azure DevOps), and only **20 yml under
`.github/workflows/`** for GitHub-side automation (markdownlint,
JIT-format, labeler, backport, copilot agents, branch-merge-flow).

apache/spark surfaced the `xml_path_*` rule-kind candidate via 49
`pom.xml` files (Maven). `dotnet/runtime` exercises the same pattern
at one order of magnitude bigger scale: 1,091 `.csproj` files plus
234 solution files (231 .slnx + 3 vendored .sln) plus ~520
`.props`/`.targets` and 257 `Directory.Build.{props,targets}`.

Concrete count at HEAD (post-sparse-checkout):

- **1,091 `.csproj` files** distributed across:
  - `src/libraries/` — **902** (the BCL: every System.* / Microsoft.Extensions.*
    has src/, ref/, tests/, often gen/ for source-generators, each its own
    csproj with its own `<TargetFrameworks>`)
  - `src/mono/` — **59** (Mono runtime + AOT compiler + sample apps)
  - `src/tools/` — **30**
  - `src/native/` — **30** (build-glue csprojs for the per-OS native libs;
    the C/C++ sources themselves are CMake)
  - `src/coreclr/` — **29** (JIT, GC, debugger, type-system tooling — most
    native code is CMake, the csprojs glue managed tooling)
  - `src/installer/` — **28**
  - `src/tasks/` — **15** (per-platform MSBuild task DLLs:
    AppleAppBuilder, AndroidAppBuilder, Crossgen2Tasks, etc.)
- **234 solution files**: **231 .slnx** (the new XML-shaped solution
  format introduced in VS 17.10; per-library "build just this one library"
  entry-points generated by the slngen tool) + **3 .sln** (all vendored
  under `src/native/external/zstd/`)
- **280 `.props`** + **187 `.targets`** files spread across `eng/` + per-area
  + per-csproj overrides
- **257 `Directory.Build.{props,targets}`** files — the MSBuild
  parent-config inheritance chain. Every csproj inherits transitively
  from every ancestor `Directory.Build.props` (and post-import from
  `Directory.Build.targets`). Drift here cascades silently.
- **76 `.props`/`.targets` under `eng/` alone** — the build-glue for the
  Arcade SDK integration:
  - `Subsets.props` (**796 lines** — the canonical "what to build" dispatch
    table; every alias in `./build.sh <subset>` maps to a csproj/proj list
    declared here)
  - `OSArch.props` (target-framework derivation from build-host arch)
  - `Versions.props` (the pinned-versions registry — ProductVersion=11.0.0,
    Major/Minor/PatchVersion numerics, PackageVersionNet{6,7,8,9}
    servicing-band pins, every UsingTool* property)
  - `packaging.targets`, `Analyzers.targets`, `illink.targets` (linker),
    `nativepgo.targets`, `nativeSanitizers.targets`, `Publishing.props`
  - `ApiCompatBaseline*.txt` — the public-API baseline registry that
    `dotnet/api-compat` diffs against
- **csproj XML-shape distribution:**
  - **1,068 of 1,091** declare `Sdk="Microsoft.NET.Sdk"` (986 plain +
    8 `Sdk.Web` + 6 `Sdk.BlazorWebAssembly` + 5 `Sdk.WebAssembly` + 1
    `Sdk.Razor` + 4 self-closing + 3 `Microsoft.Build.NoTargets` + 1 with
    `DefaultTargets`)
  - **2 outliers**: `src/workloads/workloads.csproj` uses the `<Import
    Sdk="..."/>` element-form (legitimate alternate Sdk-style) and
    `src/native/managed/cdac/mscordaccore_universal/mscordaccore_universal.csproj`
    is non-Sdk-style (evaluated only via the parent traversal)
  - **430** declare `<TargetFrameworks>` (multi-target — the BCL pattern:
    every library targets `$(NetCoreAppCurrent);$(NetCoreAppPrevious);
    $(NetCoreAppMinimum);netstandard2.0;$(NetFrameworkMinimum)` to ship
    the same DLL into every supported SDK band)
  - **517** declare `<TargetFramework>` (single-target — typically tests +
    tooling pinned to one TFM, often via `Condition="..."` for
    arch/OS-conditional builds)
  - **696** declare `<ProjectReference>` (intra-tree references)
  - **227** declare `<PackageReference>` (NuGet deps — sparse because this
    IS the .NET runtime)
- **20 `.github/workflows/*.yml`** (GitHub-side automation: labeler,
  markdownlint, jit-format, backport, branch-merge-flow, copilot-echo,
  ci-failure-scan, code-review, locker, stale, …); the actual build
  matrix lives in **186 yml under `eng/pipelines/`** (Azure DevOps)
- **`global.json`** pins both the SDK version (11.0.100-preview.3.26170.106)
  AND the msbuild-sdks (Arcade.Sdk + Helix.Sdk + SharedFramework.Sdk +
  Build.NoTargets + Build.Traversal + NET.Sdk.IL); without it `dotnet
  build` picks up the system SDK and the Arcade integration silently no-ops
- **`.config/dotnet-tools.json`** — the local-tools manifest (coverlet.console,
  dotnet-reportgenerator-globaltool, microsoft.dotnet.xharness.cli,
  microsoft.visualstudio.slngen.tool)
- **`NuGet.config`** — clears fallback folders + restricts to the
  Microsoft-internal Azure DevOps feeds (dotnet-public, dotnet-tools,
  dotnet-eng, dotnet-libraries, dotnet10, dotnet11). Without it,
  `dotnet restore` falls through to nuget.org and can't resolve the
  prerelease Arcade SDK pinned in `global.json`.
- **MIT license + Microsoft .NET patent grant** — `LICENSE.TXT` (MIT),
  `PATENTS.TXT` (the Microsoft .NET patent grant — distinct from the MIT
  copyright grant), `THIRD-PARTY-NOTICES.TXT` (every transitively-bundled
  native dependency: zlib-ng, libunwind, brotli, libffi, …)
- **`.markdownlint.json`** — the Markdown lint config used by
  `.github/workflows/markdownlint.yml`
- **`.devcontainer/`** — Codespaces-ready dev environment with per-target
  Dockerfiles (`android/`, `wasm/`, `wasm-multiThreaded/`, `libraries/`)
- **`.github/CODEOWNERS`** (112 lines) — per-area ownership; consumed by
  the GitHub PR-reviewer auto-assignment + the labeler models

Every csproj is Sdk-style + has a TargetFramework(s) declaration.
~10 invariants per csproj could be expressed as XML-path queries if
alint had `xml_path_*`; today the config falls back to
`file_content_matches` regex against the XML text.

The configured **60-rule** [`/.alint.yml`](.alint.yml) covers every
structural assertion the existing tooling makes about repo *state*,
plus several dotnet/runtime doesn't enforce today (per-area
`Directory.Build.props` presence, `eng/Versions.props` numeric-shape
discipline, `NuGet.config` fallback-folders clearing).

dotnet/runtime is the second repo (after spark) to surface the
`xml_path_*` rule-kind candidate at production scale. The cumulative
inventory across the sparse-checkout: 1,091 csprojs + 231 .slnx +
257 Directory.Build.* + 467 .props/.targets + 76 eng/ build-glue
files = **~2,300 distinct XML manifests** where structural assertions
("Sdk attribute is one of {NET.Sdk, NET.Sdk.Web, …}",
"TargetFrameworks references only known TFM properties from
Versions.props", "every `<ItemGroup>` subset entry resolves to a
csproj that exists") are bottlenecked by alint's lack of XML-aware
path queries. spark + dotnet/runtime = 2 sources, both at production
scale, both surfacing the same structural pattern.

No `csharp@v1` / `dotnet@v1` bundled ruleset exists today. alint
ships rust@v1, java@v1, python@v1, node@v1, go@v1 — but no .NET
equivalent. A bundled `dotnet@v1` ruleset covering the per-csproj
XML-shape uniformity, the global.json / NuGet.config /
Directory.Build.* triad, and the bin/obj/artifacts/ hygiene set
would consolidate ~12 of the 14 dotnet-specific rules in this
config into one `extends:` line.

### Per-csproj shape — the polyglot conventions

This is where the **`xml_path_*` candidate's necessity becomes
obvious**. Every csproj in dotnet/runtime should:

| Invariant | Today (regex `file_content_matches`) | With v0.10 `xml_path_*` |
|---|---|---|
| Root element is `<Project>` | `(?m)^<Project(\s|>|/)` (with BOM gymnastics) | `xml_path_exists: $.Project` |
| Sdk attribute is one of {NET.Sdk, NET.Sdk.Web, NET.Sdk.BlazorWebAssembly, NET.Sdk.WebAssembly, NET.Sdk.Razor, Microsoft.Build.NoTargets, Microsoft.Build.Traversal} | Long alternation regex against the file text | `xml_path_matches: $.Project[@Sdk]` |
| Has either `<TargetFramework>` or `<TargetFrameworks>` (mutually exclusive) | `<TargetFramework[s]?(\s|>)` (counts substring matches; can't enforce mutual exclusion) | `xml_path_count: $.Project.PropertyGroup./TargetFramework[s]?/ == 1` |
| TargetFrameworks references only known TFM variables from `eng/Versions.props` | Not expressible | `xml_path_matches: $.Project.PropertyGroup.TargetFrameworks; matches: '^\$\((NetCoreAppCurrent\|NetCoreAppPrevious\|NetCoreAppMinimum\|NetFrameworkMinimum\|NetCoreAppToolCurrent\|netstandard2\.0)\)' (with the variable name set declared elsewhere) |
| `<EnableNullable>true</EnableNullable>` (where the area-level Directory.Build.props makes it the convention; `src/libraries/Directory.Build.props` does this for non-test csprojs) | Per-csproj regex check | `xml_path_equals: $.Project.PropertyGroup.Nullable == "enable"` |
| `<RootNamespace>` (66 csprojs declare one) + `<AssemblyName>` (32 csprojs declare one) match the file-system path | Not expressible | `xml_path_equals` against derived path |
| `<PackageReference Include="..." Version="..." />` versions match `eng/Versions.props` declarations | Not expressible | Cross-file `xml_path_equals` check |
| Every `<ProjectReference Include="..." />` resolves to an existing csproj | Not expressible (would need path-resolution + XML extraction) | `xml_path_resolves: $.Project.ItemGroup.ProjectReference[@Include]` |

8 distinct invariants; alint expresses 3 today (with regex
fallbacks), needs `xml_path_*` for the other 5. Across 1,091 csprojs,
the cumulative drift exposure is large enough to warrant the
primitive's design cost.

## What maps to existing alint rules

The 60-rule [`/.alint.yml`](.alint.yml) breaks down as:

- **3 bundled rulesets** (`oss-baseline`, `ci/github-actions`,
  `hygiene/no-tracked-artifacts`) — pull in roughly **45 rules**
  between them
- **1 source-header rule** — `dotnet-runtime-source-has-mit-header`
  with the canonical 2-line MIT preamble used by every Microsoft .NET
  Foundation project (`Licensed to the .NET Foundation under one or
  more agreements`); excludes `src/native/external/**` (vendored:
  zlib-ng, libunwind, brotli) + `src/coreclr/pal/inc/rt/cpp/**` +
  `src/mono/mono/**` (the Mono fork's LGPL header history) + per-csproj
  ref/ stubs (codegen)
- **8 build-system anchor rules** — `dotnet-runtime-global-json-present`
  + `dotnet-runtime-global-json-pins-sdk-version` (json_path_matches) +
  `dotnet-runtime-global-json-pins-arcade-sdk` +
  `dotnet-runtime-arcade-sdk-version-format` +
  `dotnet-runtime-nuget-config-{present,clears-fallback-folders}` +
  `dotnet-runtime-{root-directory-build-props,root-directory-build-targets,
  eng-versions-props,eng-subsets-props,config-dotnet-tools}-present`
- **1 per-area Directory.Build.props presence rule** — `for_each_dir`
  over `src/{coreclr,libraries,mono,installer,tasks,tools,samples}`
  requiring `Directory.Build.props` (NOTE: `src/native/` excluded
  because it's CMake-driven; only `src/native/managed/` carries one)
- **2 per-csproj XML-shape rules** — `dotnet-runtime-csproj-uses-net-sdk`
  + `dotnet-runtime-csproj-declares-target-framework`. Both fall back
  to `file_content_matches` regex against the XML text; the cleaner
  expression needs `xml_path_*`.
- **1 per-library .slnx presence rule** — spot-check on
  `src/libraries/System.Text.Json/`; the full "every src/libraries/<name>/
  has <name>.slnx" check needs `xml_path_*` to extract the project list
  from each .slnx.
- **1 MSBuild .props/.targets root-element shape rule** —
  `dotnet-runtime-msbuild-files-have-project-root` with regex fallback
  (no line-anchor; whole-file substring match because dotnet/runtime
  files commonly start with comment block OR UTF-8 BOM)
- **6 governance + community-doc rules** — `dotnet-runtime-codeowners-present`,
  `dotnet-runtime-third-party-notices-present`,
  `dotnet-runtime-patents-txt-present`, `dotnet-runtime-security-md-present`,
  `dotnet-runtime-markdownlint-config-present`,
  `dotnet-runtime-devcontainer-present`
- **4 hygiene rules** — `dotnet-runtime-no-tracked-{bin,obj,artifacts,vs-folder}`
  with `git_tracked_only: true`
- **2 `eng/Versions.props` numeric-shape rules** —
  `dotnet-runtime-versions-props-product-version-format` +
  `dotnet-runtime-versions-props-major-minor-patch-numeric`
- **1 `eng/formatting/format.sh` presence rule** — wraps the
  dotnet/format entry-point
- **1 GHA SHA-pinning re-statement** for the 20 in-repo workflows

## What needs new alint primitives

Five patterns specific to dotnet/runtime that don't fit any current
rule (most re-confirm gaps from earlier case studies):

### 1. `xml_path_matches` / `xml_path_equals` (re-confirms spark; v0.10 ship-target)

dotnet/runtime is the second repo to surface the `xml_path_*`
gap, and the first to exercise it at full scale: 1,091 csprojs +
231 .slnx + 257 Directory.Build.* + ~520 .props/.targets +
76 eng/ build-glue files = ~2,300 distinct XML manifests in
the sparse-checkout. The current config falls back to
`file_content_matches` regex against the XML text, which works for
the canonical Sdk-attribute pattern but misses:

- Mutual-exclusion of `<TargetFramework>` vs `<TargetFrameworks>`
  (the regex `<TargetFramework[s]?(\s|>)` matches both; can't assert
  exactly one)
- Validating that `<TargetFrameworks>` references only known TFM
  variables (`$(NetCoreAppCurrent)`, `$(NetCoreAppPrevious)`, etc.)
- Asserting `<Nullable>enable</Nullable>` per area-level convention
  (every area's Directory.Build.props sets a different default)
- Cross-csproj `<ProjectReference Include="..." />` resolution
- `<PackageReference Version="..." />` ↔ `eng/Versions.props` value
  consistency

Two demand sources (spark + dotnet/runtime); the structured-query
family becomes complete (json/yaml/toml/xml) when `xml_path_*` ships.
Per launch-evidence.md, `xml_path_*` is now a v0.10 ship-target.

### 2. Bundled `dotnet@v1` (or `csharp@v1`) ruleset (net-new)

alint ships **`rust@v1`, `java@v1`, `python@v1`, `node@v1`, `go@v1`**
— but no C#/.NET equivalent. dotnet/runtime is the first P2b case
study where this gap is the dominant story. **12 of 14
dotnet-specific rules in this config could be consolidated into a
single `dotnet@v1` extends: line:**

- csproj-uses-net-sdk
- csproj-has-target-framework{s}
- root-directory-build-{props,targets}-present
- root-global-json-present + pins-sdk-version + pins-arcade-sdk
- root-nuget-config-present + clears-fallback-folders
- areas-have-directory-build-props (parameterised by area-list)
- no-tracked-bin / no-tracked-obj / no-tracked-artifacts / no-tracked-vs-folder
- msbuild-files-have-project-root

Adopters could then drop a single line:

```yaml
extends:
  - alint://bundled/oss-baseline@v1
  - alint://bundled/dotnet@v1               # ← NEW v0.10 ship-target
  - alint://bundled/ci/github-actions@v1
  - alint://bundled/hygiene/no-tracked-artifacts@v1
```

…and pick up the entire .NET/MSBuild discipline check set without
restating it. v0.10 ship-target. Adopter surface includes every
dotnet/aspnetcore, dotnet/sdk, dotnet/maui, dotnet/efcore,
microsoft/orleans, microsoft/dapr, and every Azure SDK repo — the
ruleset would land in dozens of adopter repos with zero per-repo
customisation.

A `csharp@v1` companion ruleset focusing on Roslyn-driven facts
(public-API XML doc presence, `Pure` attribute discipline,
`Nullable` enablement) could ship later if demand surfaces; the
shape is closer to AST analysis than file-shape checks, so it
likely belongs as a dotnet-format wrapper.

### 3. `eng/Subsets.props` `<ItemGroup>` ↔ on-disk csproj resolution (re-confirms spark + extends `registry_paths_resolve`)

`eng/Subsets.props` (796 lines at HEAD) is the canonical "what to
build" dispatch table. Every alias in `./build.sh <subset>` maps
to an `<ItemGroup>` of `<ProjectFile Include="..." />` entries.
Today: nothing checks that every entry resolves to an on-disk
csproj. Drift here causes `./build.sh <subset>` to silently
no-op for the missing entry (MSBuild's ItemGroup with no matches
just produces an empty subset).

Same shape as spark's Maven `<modules>` ↔ on-disk dir resolution
+ rust-lang `triagebot.toml` glob-resolution + 5 other repos
already on the `registry_paths_resolve` candidate list.
dotnet/runtime adds an 8th demand source, extending the shape to
XML-extracted (rather than text-line) registries.

### 4. .slnx ↔ csproj cross-reference (net-new shape; same v0.10 family as #1)

231 `.slnx` files at HEAD; each declares a list of projects via
`<Project Path="..." />` elements. Today: nothing checks that
every project entry resolves to an on-disk csproj. Conversely,
every csproj should appear in at least one .slnx (otherwise it's
an orphan that the slngen tool will silently drop on the next
regeneration).

Same family as #3 (XML-extracted registry) and conceptually
identical to spark's pom.xml `<modules>` shape. Defers to the
v0.10 `xml_path_*` + `registry_paths_resolve` combination.

### 5. `dotnet-tools.json` ↔ `global.json` Arcade SDK version coherence (re-confirms `cross_file_value_equals`)

The `.config/dotnet-tools.json` `tools.<tool>.version` strings AND
the `global.json` `msbuild-sdks.<sdk>` versions should be coherent:
both reference the same Arcade build (e.g. `11.0.100-preview.3.26170.106`
in global.json + a similarly-pinned coverlet/xharness/slngen in
dotnet-tools.json). Drift here means the local-tools restore can
fail because the pinned tool can't resolve against the SDK.

Same shape as the `cross_file_value_equals` candidate that's
already past-saturation (8+ sources). dotnet/runtime adds a 9th
source. Already-funded for v0.10 design.

## Gap (no bundled `csharp@v1` / `dotnet@v1` ruleset today)

The most prominent gap surfaced by this case study. Of the 5
bundled per-language rulesets alint ships (rust@v1, java@v1,
python@v1, node@v1, go@v1), none cover the .NET ecosystem. The
absence means every .NET adopter has to restate the same ~12 rules
in their own config.

Recommended composition for `dotnet@v1`:

| Rule | Shape |
|---|---|
| `dotnet-csproj-uses-net-sdk` | `<Project Sdk="Microsoft.NET.Sdk(*?)">` regex (or `xml_path_*` once it ships) |

## What's out of alint's scope (kept on the existing tool)

Listed by category for clarity:

- **MSBuild expression evaluation** — every csproj's
  `<TargetFrameworks>` evaluates against `eng/Versions.props` +
  `eng/Configurations.props` + per-area Directory.Build.props +
  conditional `Condition="..."` expressions. alint can assert that
  the variable references EXIST, not that they resolve to the right
  values. dotnet/format / dotnet build / Visual Studio handle the
  evaluation.
- **Roslyn AST analysis** (dotnet/format, dotnet/roslyn
  analyzers) — alint deliberately doesn't try to be a parser. The
  `eng/formatting/format.sh` entry-point handles this; alint just
  asserts the script's presence.
- **Public-API surface diff** (`eng/ApiCompatBaseline*.txt` ↔
  dotnet/api-compat) — parses .NET assembly metadata to diff the
  public surface against the previous shipped version. Binary-shape
  check; STAYS on dotnet/api-compat.
- **dotnet/format** — Roslyn-driven C# style enforcer. alint shells
  out via `eng/formatting/format.sh` (advisory).
- **markdownlint** (`.github/workflows/markdownlint.yml`) — Markdown
  AST aware checks. alint covers Markdown trailing-whitespace +
  final-newline + bidi-controls; the deeper Markdown semantics
  (heading-hierarchy, link-validity, code-block-shape) belong to
  markdownlint.
- **Azure DevOps pipelines** (`eng/pipelines/` — 186 yml) — bundled
  `ci/github-actions@v1` doesn't apply. A bundled
  `azure-pipelines@v1` ruleset is a candidate for v0.11+ but
  single-source today (only dotnet/* uses Azure Pipelines as the
  primary CI surface in the launch-evidence corpus).
- **NuGet package signing** (`eng/Sign*` + the Microsoft signing
  service) — operational, not a structural assertion.
- **Helix test-orchestration** (microsoft.dotnet.xharness.cli + the
  Helix.Sdk pipelines) — runs platform-specific test runners on
  the per-OS test infrastructure. Operational; out of scope.
- **`global.json` rollForward semantics** — the `"rollForward":
  "major"` field tells the dotnet host how to pick a compatible SDK
  if the exact version isn't installed. Asserting the shape is
  fine; asserting the resolved SDK is what's actually loaded would
  need runtime context.

# Design doc: architecture diagrams as a LikeC4 model (WS3, follow-on)

Status: In progress. The LikeC4 model, the rule-catalogue generator, and the
drift gates have shipped; the config-DSL domain map, the remaining behavioral
views, and the alint.org embedding are in flight.

Decisions: ADR-0005 (adopt LikeC4 for architecture diagrams). Builds on ADR-0001
(spec-driven development) and extends `architecture-as-code.md` (WS3), which
shipped the first two structural pictures.

## 1. Problem

`architecture-as-code.md` shipped a generated Mermaid crate graph and a
hand-modeled Structurizr C4 model gated on the crate set. Two gaps remained:

1. No domain/model diagrams (the rule catalogue, the config DSL) and no
   sequence/flow diagrams (the execution pipeline, config load, fix, ...). The
   architecture page describes all of these in prose only.
2. The Mermaid crate graph did not actually render on alint.org (Starlight has no
   Mermaid renderer, so it showed as a code block), making the "renders natively
   on alint.org" claim in `architecture-as-code.md` false.

Requirements for the new diagrams: provably generated and consistent (no drift),
visually polished, interactive/animated where it helps, and still renderable in
GitHub markdown.

## 2. Tool choice: LikeC4

GitHub markdown rendering is effectively Mermaid-only, while a polished
interactive renderer points away from Mermaid, so no single artifact satisfies
all four requirements. The resolution is one model with multiple targets, which
is what LikeC4 gives:

- Provable: `likec4 validate` exits non-zero on syntax errors, layout drift, and
  any dynamic-view step that references an element or relationship that does not
  exist. A spike confirmed exit 1 plus a precise source location on a broken flow.
- Polished, interactive, animated: the LikeC4 renderer supports navigation,
  drill-down, and hover-highlight; dynamic views animate step by step with
  auto-zoom. It embeds in Astro/Starlight via the LikeC4 Vite plugin, which also
  closes the render gap.
- GitHub markdown: `likec4 gen mermaid` emits one `.mmd` per view, including
  dynamic views (rendered as flowcharts). The animated sequence lives in the
  interactive renderer; GitHub gets a faithful static flowchart of the same model.
- Node-only (no Java, no Graphviz). Validated against LikeC4 1.58.0.

Alternatives rejected: Mermaid-only (behavioral diagrams would be only
vocabulary-gated, not model-provable, and not interactive); Structurizr (Java in
CI, static export, interactive viewer not cleanly embeddable in a static site);
D2 (not a C4 model, so no dynamic-view provability, and not GitHub-native). Full
rationale in ADR-0005.

## 3. Surface area

A single LikeC4 workspace at `docs/design/architecture/model/`:

- `alint.c4` (hand-authored): the C4 intent (persons, external systems, the
  `alint` system with its containers and the crates as components) plus the
  behavioral dynamic views (`checkFlow`, `configLoad`, `fixFlow`, ...), and the
  structural views (system context, containers, CLI components).
- `*.gen.c4` (generated by `xtask gen-model` from canonical sources):
  - `rule-families.gen.c4`: the rule-kind taxonomy (families to kinds) sliced
    from `docs/rules.md`. 13 families, 78 canonical kinds (the 11 aliases ride on
    their canonical kind: 78 + 11 = the 89 in `facts.json`).
  - Planned: `config-model.gen.c4` (the config-DSL domain map from the JSON
    schema) and, if the crate graph moves fully into generation,
    `crate-deps.gen.c4`.

`crate-graph.md` (Mermaid) and `workspace.dsl` (Structurizr) are retained through
the transition and retired once the LikeC4 model subsumes them.

## 4. Drift control (two layers)

- Generated fragments use a byte-gate. `xtask gen-model --check` regenerates the
  `*.gen.c4` in memory and content-diffs the committed files (mirrors
  `gen-arch`/`gen-facts`): wired into `ci/scripts/docs.sh`, LF-pinned in
  `.gitattributes`, with a freshness unit test. These cannot drift from source.
- The hand-authored model uses validate plus a vocabulary gate.
  - `likec4 validate` (via `ci/scripts/likec4.sh`) proves structural integrity:
    every flow step references a real, declared element and relationship.
  - A `gen-model` gate and unit test assert that the crate elements declared in
    `alint.c4` equal the `cargo metadata` workspace members (mirrors `gen-arch`'s
    `workspace.dsl` gate), so a crate added or removed without updating the model
    fails CI.
  - The flow topology (the order of steps) is reviewed intent; the vocabulary
    (crate, family, format, fact-kind, ... names) is gated against the canonical
    sets that `facts.json` derives from.

`likec4 validate` needs Node on the runner (ADR-0005 chose alint-repo gating, not
alint.org). `ci/Containerfile` gains Node 22; until the runner is rebuilt,
`likec4.sh` detects the missing Node and skips with a loud warning rather than
failing CI.

## 5. Targets

- alint.org: the `.c4` model ships in the docs bundle (`docs-export`) and
  alint.org renders the views interactively via the LikeC4 Vite plugin (Phase 5).
- GitHub: `likec4 gen mermaid` exports a per-view `.mmd` for embedding in repo
  markdown (the architecture page prose sections).

## 6. View catalogue and page placement

One LikeC4 view embeds on any page via `<likec4-view view-id="...">`, so the
single gated model is a site-wide diagram library: each page embeds the views it
needs and every diagram stays gated centrally. The question is which view-ids
embed where, plus which new views are worth modeling.

### Built (26 views)

Structural: system context, containers, CLI components, crate dependency graph
(gen-arch), config-DSL domain map, rule catalogue + 13 per-family views.

Behavioral: checkFlow (execution pipeline), configLoad (extends trust boundary,
ADR-0004), fixFlow, dispatchFlow (read-coalescing, ADR-0003), factsFlow
(when-gating), lspFlow, ciActionFlow (SARIF), docsAsCodeFlow.

### Build tiers

- Tier 1 (ships with the embedding; views already built): the Architecture page,
  Integrations/github-actions, Integrations/editors, Configuration/Concepts. Pure
  embedding, no new modeling.
- Tier 2 (build next): ruleTypeModel, addRuleKindFlow, monorepoNesting,
  distributionFlow, outputFormatsFan, walkerFlow, templateFlow.
- Tier 3 (nice-to-have): perfGatingFlow, pluginModel, the security set,
  editorArch, marketing hero diagrams.

Each new view anchors in a real source (distributionFlow in release.yml plus
install.sh; outputFormatsFan in the `Format` enum; monorepoNesting in the bundled
rulesets), keeping the generate-and-gate ethos.

### Mechanics caveats

- Synced docs are plain `.md`, not `.mdx`, so embedding uses the LikeC4
  web-component (`<likec4-view>` works in raw-HTML markdown once the script is
  registered site-wide), not a component import.
- Marketing `.astro` landings are Lighthouse-sensitive (near zero JS). For those,
  prefer a static `likec4 export svg` image over the interactive embed.
- ruleTypeModel is a class/ER shape, the one type LikeC4 strains on (like the
  config-DSL map): model it as containment plus relationships, or emit a Mermaid
  classDiagram for that one.

## 7. Config-DSL representation (decision)

LikeC4 is a C4/containment tool, not an entity-relationship tool. The config DSL
is modeled as a LikeC4 domain map (entities and relationships, uniform style),
not a field-level class/ER diagram. The field, type, and cardinality detail
already lives in the generated JSON-schema reference, so this keeps one visual
language and avoids adding a second (Mermaid) renderer to the site for a single
diagram.

  `ci/scripts/likec4.sh` (`likec4 validate`).

  `model_crate_set_matches_cargo_metadata`, plus parser unit tests.
- `.gitattributes`: `docs/design/architecture/model/*.gen.c4 text eol=lf`.

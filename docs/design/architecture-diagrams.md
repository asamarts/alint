# Design doc: architecture diagrams as a LikeC4 model (WS3, follow-on)

Status: Implemented (pending merge + deploy). The single LikeC4 model (39 views:
19 structural, 20 dynamic), the generated `*.gen.c4` fragment and its drift
gates, the config-DSL domain map, the alint.org web-component embedding with
light/dark sync, and the GitHub-facing Mermaid gallery (`DIAGRAMS.md`) have all
shipped. Remaining: a runner rebuild (Node) flips `likec4 validate` and
`gen-mermaid --check` from skip to hard gate, and `crate-graph.md` /
`workspace.dsl` retire once the model subsumes them.

Decisions: ADR-0005 (adopt LikeC4 for architecture diagrams). Builds on ADR-0001
(spec-driven development) and extends `architecture-as-code.md` (WS3), which
shipped the first two structural pictures.

## 1. Problem

`architecture-as-code.md` shipped a generated Mermaid crate graph and a
hand-modeled Structurizr C4 model gated on the crate set. Two gaps remained:

1. No domain/model diagrams (the rule catalogue, the config DSL) and no
   sequence/flow diagrams (the execution pipeline, config load, fix, ...). The
   architecture page describes all of these in prose only.
2. The Mermaid crate graph did not actually render on alint.org (Starlight has no
   Mermaid renderer, so it showed as a code block), making the "renders natively
   on alint.org" claim in `architecture-as-code.md` false.

Requirements for the new diagrams: provably generated and consistent (no drift),
visually polished, interactive/animated where it helps, and still renderable in
GitHub markdown.

## 2. Tool choice: LikeC4

GitHub markdown rendering is effectively Mermaid-only, while a polished
interactive renderer points away from Mermaid, so no single artifact satisfies
all four requirements. The resolution is one model with multiple targets, which
is what LikeC4 gives:

- Provable: `likec4 validate` exits non-zero on syntax errors, layout drift, and
  any dynamic-view step that references an element or relationship that does not
  exist. A spike confirmed exit 1 plus a precise source location on a broken flow.
- Polished, interactive, animated: the LikeC4 renderer supports navigation,
  drill-down, and hover-highlight; dynamic views animate step by step with
  auto-zoom. It embeds in Starlight via the standalone `<likec4-view>` web
  component (a global loader registers it and syncs the Starlight light/dark
  theme), which also closes the render gap.
- GitHub markdown: `likec4 gen mermaid` emits one `.mmd` per view, including
  dynamic views (rendered as flowcharts). `xtask gen-mermaid` assembles the
  curated set into `DIAGRAMS.md`; the animated sequence lives in the interactive
  renderer, and GitHub gets a faithful static flowchart of the same model.
- Node-only (no Java, no Graphviz). Validated against LikeC4 1.58.0.

Alternatives rejected: Mermaid-only (behavioral diagrams would be only
vocabulary-gated, not model-provable, and not interactive); Structurizr (Java in
CI, static export, interactive viewer not cleanly embeddable in a static site);
D2 (not a C4 model, so no dynamic-view provability, and not GitHub-native). Full
rationale in ADR-0005.

## 3. Surface area

A single LikeC4 workspace at `docs/design/architecture/model/`:

- `alint.c4` (hand-authored): the C4 intent (persons, external systems, the
  `alint` system with its containers and the crates as components), the
  `engineTypes` domain (the rule-execution type model), the behavioral dynamic
  views (`checkFlow`, `configLoad`, `fixFlow`, ...), and the structural views
  (system context, containers, CLI components, `ruleTypeModel`).
- `config-model.c4` (hand-authored): the config-DSL domain map. Its top-level
  `Config` fields are gated against the JSON schema's root properties (section
  4), so the map can't drift from the config surface.
- `rule-families.gen.c4` (generated by `xtask gen-model` from `docs/rules.md`):
  the rule-kind taxonomy (families to kinds). 13 families, 78 canonical kinds
  (the 11 aliases ride on their canonical kind: 78 + 11 = the 89 in `facts.json`).

`crate-graph.md` (Mermaid) and `workspace.dsl` (Structurizr) are retained through
the transition and retired once the LikeC4 model subsumes them.

## 4. Drift control (two layers)

- Generated fragments use a byte-gate. `xtask gen-model --check` regenerates the
  `*.gen.c4` in memory and content-diffs the committed files (mirrors
  `gen-arch`/`gen-facts`): wired into `ci/scripts/docs.sh`, LF-pinned in
  `.gitattributes`, with a freshness unit test. These cannot drift from source.
- The hand-authored model uses validate plus a vocabulary gate.
  - `likec4 validate` (via `ci/scripts/likec4.sh`) proves structural integrity:
    every flow step references a real, declared element and relationship.
  - `gen-model --check` runs five gates over the hand-authored model, each with
    a unit test: the `alint.c4` crate elements equal the `cargo metadata`
    workspace members; the crate-to-crate edges equal the `cargo metadata`
    runtime dependency edges (the gap that once let `alint-lsp -> alint-rules` go
    missing); the `config-model.c4` `Config` fields equal the JSON schema's root
    properties; the taxonomy covers every kind registered in `all_kinds.yaml`;
    and every `view-id` embedded on a doc surface names a real view in the model,
    so a renamed or removed view can't silently render an empty diagram.
  - The flow topology (the order of steps) is reviewed intent; the vocabulary
    (crate, family, format, fact-kind, ... names) is gated against the canonical
    sets that `facts.json` derives from.

`likec4 validate` needs Node on the runner (ADR-0005 chose alint-repo gating, not
alint.org). `ci/Containerfile` gains Node 22; until the runner is rebuilt,
`likec4.sh` detects the missing Node and skips with a loud warning rather than
failing CI.

## 5. Targets

- alint.org: the `.c4` model ships in the docs bundle (`docs-export`).
  `scripts/build-likec4.mjs` runs `likec4 gen webcomponent` over the synced model
  into a self-registering bundle, and a global loader (in the Starlight head)
  lazy-loads it only on pages that embed a `<likec4-view>` and mirrors the
  Starlight `data-theme` onto each view's `color-scheme`. Not the LikeC4 Vite /
  React plugin: the standalone web component works in plain `.md`.
- GitHub: `xtask gen-mermaid` assembles the curated views into a single
  GitHub-only doc, `docs/design/architecture/DIAGRAMS.md`. GitHub strips the
  `<likec4-view>` embeds, so the dual-surfaced `ARCHITECTURE.md` (which is also
  the synced alint.org architecture page) links to `DIAGRAMS.md` rather than
  embedding Mermaid that would double-render on alint.org. The model's Mermaid
  v11 node syntax is normalized to classic `[...]` so it renders on GitHub's
  older Mermaid.
- Marketing landings: near-zero-JS `.astro` pages embed a committed static SVG
  (`likec4 gen d2`, then a browser-free `d2` render that carries both light and
  dark in one SVG via a prefers-color-scheme media query), not the interactive
  bundle.

## 6. View catalogue and page placement

One LikeC4 view embeds on any page via `<likec4-view view-id="...">`, so the
single gated model is a site-wide diagram library: each page embeds the views it
needs and every diagram stays gated centrally. The question is which view-ids
embed where, plus which new views are worth modeling.

### Built (39 views, all embedded)

Structural: system context, containers, CLI components, crate dependency graph
(gen-arch), config-DSL domain map, rule catalogue + 13 per-family views.

Behavioral: checkFlow (execution pipeline), configLoad (extends trust boundary,
ADR-0004), fixFlow, dispatchFlow (read-coalescing, ADR-0003), factsFlow
(when-gating), lspFlow, ciActionFlow (SARIF), docsAsCodeFlow.

### Build tiers (status)

All 39 model views are built, validated, gated, and embedded across ~30 pages
per the table above. The alint.org gallery page (`about/architecture-diagrams`)
is the full explorer; the per-page embeds place each view in its context, and
`gen-mermaid` mirrors the same curated set into `DIAGRAMS.md` for GitHub.

- Tier 1 (built + embedded): system context, containers, CLI components, crate
  graph, config-DSL map, rule catalogue, and the core flows.
- Tier 2 (built): ruleTypeModel, addRuleKindFlow, monorepoNesting,
  distributionFlow, outputFormats, walkerFlow, templateFlow.
- Tier 3 (built): perfGatingFlow, pluginModel, pathConfinement + trojanSourceFlow
  (security), editorArch. The marketing hero stays a static-SVG export of an
  existing view (e.g. checkFlow), not a separate model view.

Each view anchors in a real source (distributionFlow in release.yml plus
install.sh; outputFormats in the `Format` enum; monorepoNesting in the bundled
rulesets), keeping the generate-and-gate ethos.

### Mechanics caveats

- Synced docs are plain `.md`, not `.mdx`, so embedding uses the LikeC4
  web-component (`<likec4-view>` works in raw-HTML markdown once the script is
  registered site-wide), not a component import.
- Marketing `.astro` landings are Lighthouse-sensitive (near zero JS), so they
  embed a committed static SVG rather than the interactive bundle. `likec4 export`
  has no SVG target (only PNG/JPG via a headless browser), so the SVGs come from
  `likec4 gen d2` piped through a browser-free `d2` render.
- ruleTypeModel and the config-DSL map are class/ER shapes, the one type LikeC4
  strains on; both are modeled as containment plus relationships (a LikeC4 domain
  map), not a field-level class diagram, to keep one visual language (see
  section 7).
- GitHub strips the `<likec4-view>` web component, and Starlight has no Mermaid
  renderer, so the two galleries can't share one file: alint.org gets the web
  component, GitHub gets `DIAGRAMS.md`. `gen-mermaid` curates both from the same
  gallery order, and the model's v11 node syntax is normalized to classic
  Mermaid so GitHub's older renderer accepts it.

## 7. Config-DSL representation (decision)

LikeC4 is a C4/containment tool, not an entity-relationship tool. The config DSL
is modeled as a LikeC4 domain map (entities and relationships, uniform style),
not a field-level class/ER diagram. The field, type, and cardinality detail
already lives in the generated JSON-schema reference, so this keeps one visual
language and avoids adding a second (Mermaid) renderer to the site for a single
diagram.

## 9. Tests and gates

- `ci/scripts/docs.sh`: `gen-model --check` (byte-freshness of the generated
  fragment plus the five model gates), then `ci/scripts/likec4.sh`
  (`likec4 validate`), then `gen-mermaid --check` (byte-freshness of
  `DIAGRAMS.md`). The last two are Node-guarded and skip until the runner ships
  Node.
- `xtask` unit tests: `gen_model_check_passes_on_committed_tree`, the five
  model-gate tests (crate set, crate edges, config keys, taxonomy completeness,
  embedded view-ids), the `gen-mermaid` parser tests, plus shared parser tests.
- alint.org `scripts/build-likec4.mjs`: fails if pages embed `<likec4-view>`
  with no model present, and validates every alint.org-side view-id (content
  embeds, the loader `SEQUENCE`, the landing `VIEWS`) against the synced model.
- `.gitattributes`: `docs/design/architecture/model/*.c4` and
  `docs/design/architecture/DIAGRAMS.md` are `text eol=lf`.

# v0.21: witforge adoption and the WIT gate (W2-7)

Status: Plan (2026-10-31). The owner's decisions are in section 3; the contract's status is
recorded in [ADR-0027](../../adr/0027-plugin-contract-0-1-stays-a-draft.md). The gate this plan
clears is [ADR-0025](../../adr/0025-v021-pre-release-decisions.md) decision 4: v0.21.0 is not
tagged until witforge 0.1.0 is published and pinned and the contract's check, generation, and
regeneration `--check` run in default CI. It is audit item W2-7 in
[`pre-release-audit.md`](pre-release-audit.md) and the one blocked row in
[`r8-readiness.md`](r8-readiness.md).

## 1. Where things stand

- **witforge** (`asamarts/witforge`, private) has a 0.1.0 candidate on its `main`: the subset
  checker, the wire lock, and the Rust, protobuf, and glue emitters, with the version set to
  0.1.0, publishing enabled, and a package dry run done. It is not tagged or published. Its
  release checklist requires alint's consumer pull request (#409) to be merged first.
- **alint** has the `alint:plugin@0.1.0` WIT draft at `wit/alint-plugin/v0.1/` and the
  hand-written `alint_core::plugin_api` it describes. Before #409, nothing in CI checked the
  WIT, and nothing compared it with `plugin_api`.
- Two pull requests from another session were open: #408 and #409.

## 2. Review of #408 and #409

### #408 (closed 2026-10-31)

#408 combined `key_parity` fixes with an early form of the consumer crate. Its `key_parity`
commits had already landed through #407 (its tip has the same tree as #407's squash), and its
witforge commit is a subset of #409. Nothing in it was left to merge, so it was closed and its
two branches deleted.

### #409 (taken over 2026-10-31)

#409 adds `crates/alint-witforge-consumer`, the code witforge generates from the WIT, and
`ci/scripts/witforge-consumer.sh`. The generated content is genuine: the plain and glue modules
are witforge's output passed through rustfmt, and the prost and proto3-JSON modules are exactly
what prost-build 0.14 and pbjson-build 0.9 produce from witforge's schema. The review found
these problems, all fixed in the pull request:

| # | Problem | Fix |
|---|---|---|
| 1 | The script generated into a temporary directory and ran `--check` against that same directory, so it never compared anything with the committed files. Pointed at them, `--check` failed: the committed copies had been reformatted by rustfmt. | The committed plain and glue modules are witforge's output byte for byte, kept out of rustfmt with `#[rustfmt::skip]`, and the script runs `rust`, `proto`, and `glue` with `--check` against them (`--write` regenerates them). It pins the witforge version and no longer runs the crate's tests, which run with the workspace tests on every platform. |
| 2 | The prost and proto3-JSON code was committed, generated by tools nothing checked. | `build.rs` generates it from the committed, witforge-checked `proto/v0.proto` (parsed by `protox`, so no `protoc` is needed), as witforge's own end-to-end test does. |
| 3 | The check had no controls, so it could pass by checking nothing. | `ci/scripts/test-witforge-consumer.sh` runs it on copies of the tree: the unmodified copy must pass, and a changed file (each of the four), an extra file, a missing file, and a wire lock missing an entry must each fail with witforge's message for that case. |
| 4 | Nothing compared `plugin_api` with the WIT, and they had drifted: the WIT's analyzer input has `max-findings`, `plugin_api` passed `Limits::max_rows`. | `plugin_api`'s inputs now carry `max_rows` and `max_findings` as the WIT names them, and `tests/plugin_api.rs` converts every type both ways without `..` patterns and serves each trait through the other (ADR-0027 decision 3). |
| 5 | Generated files had no line-ending pin, so Windows checkouts with `autocrlf` would report them stale. | `.gitattributes` pins the WIT tree and the generated files to LF. |

The pull request also marked the readiness report's WIT row as passed on a manual run. ADR-0025
decision 4 says a manual run does not count, so the row stays blocked until step 6 below.

## 3. Decisions (2026-10-31)

1. **#409: take it over in place.** Rebased onto `main`, with the fixes above pushed to its
   branch, and merged when CI is green. Merging it meets witforge's release-checklist gate.
2. **#408: close it and delete its branches.** Done.
3. **Contract 0.1 stays a draft in v0.21** (ADR-0027). The first release that loads plugins (P2)
   freezes it with a `released` manifest and a freeze check.
4. **witforge: clean its history, make it public, publish it.** Before the repository becomes
   public, its history is rewritten to drop files that must stay private (a vendored binary of
   a private tool, and task-tracking metadata naming a personal account), the commit references
   in its own records are remapped to the rewritten commits, and CI gates that need the private
   tool run only on the private runner or are removed. Each of the history rewrite and the
   visibility change is confirmed with the owner right before it is done.

## 5. The W2-7 job

A job in the default CI workflow, on Linux:

1. install the pinned release: `cargo install witforge-cli --version =0.1.0 --locked`, cached by
   version;
2. run `ci/scripts/witforge-consumer.sh`, which checks the WIT and regenerates the committed
   output with `--check`;
3. run `ci/scripts/test-witforge-consumer.sh` with `WITFORGE_REQUIRED=1`, so a missing binary
   fails instead of skipping.

The consumer crate's tests (the protobuf and proto3-JSON round trips and the `plugin_api`
comparison) already run with the workspace tests on every platform, so the job does not repeat
them. A witforge upgrade changes `WITFORGE_VERSION` in the script, the job's install pin, and
the committed output in one pull request.

## 6. Open items

- **`plugin-info`.** The conversion test leaves it out: `plugin_api` has no counterpart, and the
  handshake that carries it arrives with P2, which adds both.
- **The consumer crate's end.** P2 replaces `alint-witforge-consumer` with the published
  `alint-plugin-api` crate generated from the same WIT; the controls and the W2-7 job move with
  it.
- **Dependencies.** The consumer crate adds three duplicate crate versions to `cargo deny`'s
  warnings, all in an unpublished crate: `base64` 0.22 through the `pbjson` runtime, and
  `foldhash` 0.1 and `itertools` 0.14 through the build-time generators.
- **#409's branch.** Another session's worktree has it checked out, so it is left in place
  after the merge and deleted by name once that worktree is gone.

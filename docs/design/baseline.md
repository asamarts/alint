# Design doc: baseline mode (grandfathering existing violations)

Status: Draft. (Draft | Implemented in <commit> | Superseded by <doc>.)
Decisions: [ADR-0006](../adr/0006-baseline-suppression.md) (new persistent suppression mechanism; affects pass/fail semantics).
Demand evidence: External adoption evaluation, §4.1 — *"the single feature that makes ESLint/RuboCop/etc. adoptable on legacy code, and its absence is the #1 thing that stops a team from flipping alint on as a merge gate."* Reproduced firsthand against alint 0.13.0.
Target version: Phase 4, unscheduled (post-v0.14). This doc is a draft for review; resolve §7 before implementation and move it under the assigned `docs/design/vX.Y/` directory at that time.

## 1. Problem

On a large, long-lived repository, turning on a ruleset surfaces hundreds of
pre-existing violations at once. Today the only levers are `level: off`, `when:`
gates, and `ignore:`/exclude globs — **all of which also suppress future, new
violations of the same rule**. There is no "accept the current state, fail only
on *new* violations" mode. A team that wants to adopt alint as a blocking merge
gate has to either fix everything first (often hundreds of findings) or disable
the rule entirely (losing the gate). Neither is acceptable, so they don't adopt.

This is the standard grandfathering / baseline capability every mature linter
ships for exactly this reason:

- **RuboCop** — `.rubocop_todo.yml` (generated by `--auto-gen-config`), per-`(cop,
  file)` counts.
- **ESLint** — bulk suppressions file (`eslint --suppress-all` →
  `eslint-suppressions.json`), per-`(rule, file)` counts.
- **PHPStan / Psalm / detekt** — a committed baseline file (often per-issue
  fingerprints or per-file counts).
- **golangci-lint** — `--new-from-rev` (a diff-based variant; see §3.5).

**Partial workaround that exists today:** `--changed` / `--base` lints only the
files in the diff, which approximates "don't punish old code." But it is a
*scope* filter, not a baseline: cross-file rules (`pair`, `for_each_dir`,
`file_graph`, `unique_by`, `registry_paths_resolve`, …) and existence rules
(`file_exists` et al.) consult the **full tree** by definition (documented on
`alint check --changed`), so those still fire on legacy state. A real baseline
*complements* `--changed`; it does not duplicate it (§3.5).

Without baseline mode, alint is adoptable on greenfield repos and as an advisory
(non-blocking) check, but not as a blocking gate on a large existing codebase —
the case where a structural linter has the most value.

## 2. Surface area

No DSL/schema change to rule definitions. Three additions:

### 2.1 A committed baseline file

A new artifact, default path `.alint-baseline.json` at the repo root, written by
the tool and committed. JSON (not YAML): it is machine-generated and
machine-consumed, never hand-edited (hand edits are a smell — regenerate
instead), and it shares the `schema_version`-gated, deterministic-output shape of
`facts.json` / `--format json`.

```json
{
  "schema_version": 1,
  "alint_version": "0.x.y",
  "generated_at_commit": "<git sha, optional/advisory>",
  "violations": [
    {
      "rule_id": "no-todo-comments",
      "path": "src/legacy/api.ts",
      "fingerprint": "9f2b…<hex>",
      "count": 3
    },
    {
      "rule_id": "lockfiles-only-one",
      "path": null,
      "fingerprint": "1ac0…<hex>",
      "count": 1
    }
  ]
}
```

Entries are sorted by `(rule_id, path, fingerprint)` so an unchanged tree
regenerates **byte-identically** (no spurious diff churn; gate-able like the
`gen-*` artifacts). `path` is repo-relative (forward slashes, normalised) or
`null` for repository-level violations. `count` collapses identical fingerprints
(§3.2). `alint_version` / `generated_at_commit` are advisory provenance, not part
of matching.

### 2.2 `alint baseline` — write the baseline

```
alint baseline [PATH] [--output <file>] [--changed] [--base <ref>]
```

Runs the same evaluation as `check`, then writes every current violation into the
baseline file (default `.alint-baseline.json`). Overwrites unconditionally — the
baseline is the "accept the current state" button, meant to be regenerated, not
merged by hand. Exits 0 on a successful write. `--changed`/`--base` are accepted
for symmetry but a baseline is normally whole-tree (see §7).

### 2.3 `alint check --baseline <file>` — enforce only the delta

```
alint check  --baseline <file> [other flags]
alint fix    --baseline <file> [other flags]   # see §3.4
```

Suppresses every current violation whose fingerprint is present (and not yet
exhausted) in the baseline; reports only **new** violations. Suppressed
violations do not count toward the exit code (§3.3). A one-line stderr summary
reports the suppressed count; `--show-baselined` lists them in full; stale
baseline entries (recorded but no longer firing) are surfaced as a warning so the
baseline can be re-tightened (§3.6).

A `baseline: <path>` key in `.alint.yml` is offered as a persistent alternative
to the flag so CI doesn't have to pass it every run (§7, open).

## 3. Semantics

### 3.1 The fingerprint (the crux)

A baseline must survive benign code motion (inserting lines elsewhere, moving a
file's contents around) without churning, yet **re-trigger when the offending
code is edited** and never mask a genuinely *new* violation. Per the evaluation's
explicit ask, the fingerprint is keyed on `rule_id + path + a content hash`, and
**deliberately excludes the line/column number** (which shifts on every insert
above it). The fingerprint is computed per violation as a SHA-256 (sha2 is
already a workspace dep) over a domain-separated tuple, by violation shape:

| Violation shape | Fingerprint input | Rationale |
|---|---|---|
| **path + line** (`Violation.line.is_some()`) | `rule_id ‖ path ‖ exact bytes of the offending line` | Line *number* excluded → inserts/reflows above don't churn; editing the offending line changes its bytes → re-triggers; the same offending text moved within the file keeps its hash → stays suppressed. |
| **path, no line** (file-level, e.g. `final_newline`, `file_exists`) | `rule_id ‖ path` | A file-level rule fires at most once per file; the path is the whole identity. |
| **no path** (repo-level / cross-file, e.g. `lockfiles-only-one`) | `rule_id ‖ normalised message` | The message carries the discriminating detail (which files, which key). Message wording is stable within a version; a rule-kind reword re-baselines (rare, acceptable — §4). §7 weighs a structural key instead. |

The offending line's bytes are read from the file content the engine already
walked (the `FileIndex` entry / on-disk bytes at `Violation.path`), so no second
read of unrelated files. `‖` is a length-prefixed/NUL-delimited join so
`a‖bc` and `ab‖c` can't collide. Column is intentionally not in the hash
(line-granular is the right churn/precision balance; per-column would re-trigger
on trivial intra-line edits).

### 3.2 Counting identical fingerprints

Three identical offending lines in one file produce one fingerprint with
`count: 3`. Matching is count-aware: a current run that produces *k* violations
with fingerprint *F* is suppressed for up to `baseline[F].count` of them; any
beyond that are **new**. Fix one of the three → the run produces 2, the baseline
recorded 3 → 2 suppressed, 0 new, **1 unfilled** (a stale-count signal for §3.6).
This is the RuboCop/ESLint count model applied per-fingerprint rather than
per-`(rule, file)`, giving both line-content precision *and* duplicate tolerance.

### 3.3 Enforcement pass (`check --baseline`)

1. Run the full evaluation (unchanged) → `Report`.
2. Build the current fingerprint multiset from `Report`.
3. For each fingerprint, suppress `min(current_count, baseline_count)`
   occurrences; the remainder are new.
4. Remove suppressed violations from the `Report` *before* formatting, so every
   formatter (human/json/sarif/agent/…) sees only new violations. Carry the
   suppressed total + the stale-entry list as report metadata.
5. Exit code is computed on the **post-suppression** report: only new errors
   (or, with `--fail-on-warning`, new warnings) fail. A repo whose only findings
   are baselined exits 0 — the whole point.

Dispatch class: not a rule; a **post-evaluation report transform**, sitting
between `Engine::run` and the formatter, alongside the existing notes-partition
step. Determinism: suppression is a pure function of `(Report, baseline)`; output
ordering is unchanged.

### 3.4 `fix --baseline`

`fix` applies fixers; fixing a baselined violation removes accepted debt, which is
always desirable, so `fix` ignores the baseline for *applying* fixes by default.
`--baseline` on `fix` only affects which *unfixable* violations are reported in
the post-fix summary (same suppression as `check`). After a fix run that resolves
baselined violations, `alint baseline` should be re-run to prune them (§3.6).
(Open: a `--only-baselined` fix mode to "pay down debt" — §7.)

### 3.5 Relationship to `--changed` / `--base`

They are **orthogonal filters that compose**:

- `--changed`/`--base` is a **scope** filter: which files the per-file rules run
  on (the diff). Cross-file + existence rules still see the full tree.
- `--baseline` is a **suppression** filter: which already-known violations
  (anywhere, including from the full-tree rules `--changed` can't scope) are
  accepted.

`check --changed --baseline .alint-baseline.json` = lint the diff *and* suppress
any pre-existing baselined issue that still surfaces. The baseline is what makes
the full-tree rules adoptable on legacy code; `--changed` alone cannot. This is a
strictly richer model than golangci-lint's `--new-from-rev` (diff-only, no
cross-file grandfathering).

### 3.6 Stale entries

After enforcement, a baseline fingerprint whose recorded `count` exceeded the
suppressed count matched fewer violations than recorded — the underlying issue
was (partly) fixed or its line edited. These are **stale** and surfaced as a
warning (`N baseline entr(ies) no longer fire; run \`alint baseline\` to
re-tighten`). Stale entries never *fail* the build by default (that would punish
fixing things); `--strict-baseline` to fail on stale (keep the debt strictly
monotonic) is an option (§7).

## 4. False-positive surface

The risk that matters most: **a baseline masking a genuinely new violation**
(a real regression silently suppressed). Mitigations, by failure mode:

- **Fingerprint too loose → new violation wrongly suppressed.** For file-level
  and repo-level rules the identity is exact (path / message), so a *different*
  new violation has a different fingerprint and is reported. For line rules the
  content hash means a *new, different* offending line is a different fingerprint
  → reported. The only loose case is "a new occurrence of byte-identical
  offending content in the same file beyond the recorded count" — caught by the
  count model (§3.2): the (count+1)th is new.
- **Fingerprint too tight → baseline churn.** Excluding the line number means
  inserting/deleting unrelated lines doesn't churn; only touching the offending
  line itself re-triggers (the desired "you edited it, re-justify it" behaviour).
  Whole-file reformatting that rewrites every offending line *will* re-trigger —
  acceptable and arguably correct (re-run `alint baseline` after a sweeping
  format; that is a deliberate "re-accept" action).
- **Repo-level message drift.** A rule-kind upgrade that rewords its message
  re-fingerprints its no-path violations → they re-surface after the upgrade.
  Rare, version-coupled, and visible (the stale-entry warning flags the old
  entries). §7 weighs a structural discriminator to remove this.
- **File rename → re-trigger.** `path` is in the fingerprint, so moving a file
  re-surfaces its baselined violations at the new path. Defensible (the file
  changed) but churny on large refactors; rename-following is out of scope for
  v1 (§7).
- **Masking a security violation.** A baseline is a committed, PR-reviewed
  artifact; the stale-entry warning and `--show-baselined` keep it honest. It
  carries no code-execution surface (§5). The design does **not** let a baseline
  be introduced via `extends:` (local-only, like the config) so a published
  ruleset can't ship a suppression.

## 5. Implementation notes

- **Module:** `crates/alint-core/src/baseline.rs` — `Baseline` (load/save, the
  `schema_version`-gated JSON), `fingerprint(&Violation, file_bytes) -> Hash`,
  and `apply(report, &baseline) -> (filtered_report, Suppressed, Stale)`. The CLI
  (`crates/alint/src/main.rs`) gains `cmd_baseline` and threads `--baseline`
  into `cmd_check` / `cmd_fix` (the existing `apply_only_filter` sits at the same
  layer — post-load, around `Engine::run`).
- **Dependencies:** none new. `sha2 = "0.11"` is already a workspace dep;
  `serde`/`serde_json` already used by the JSON formatter. (cargo-deny: no
  change.)
- **Reuse:** the fingerprint's path/line/message inputs are exactly the
  `--format json` violation fields, so a baseline entry is conceptually a hashed
  JSON violation — keep them aligned.
- **Constitution invariants** (`constitution.md`): *Correctness and behavior* —
  suppression is deterministic and order-preserving; the baseline file is
  deterministic, sorted, `schema_version`-gated (matching the anti-drift floor).
  *Security* — no new trust surface; the baseline path is path-confined within
  root like other read paths, and is not reachable via `extends:`.

## 6. Tests

Unit (`baseline.rs`): fingerprint stability (same tree → identical hash + identical
serialized file); line-number-independence (insert lines above → same hash);
edited-offending-line → different hash; identical-lines count collapse;
no-path/message and file-level/path fingerprints; format_version round-trip;
sorted/deterministic serialization.

e2e (`crates/alint-e2e`), the firing + silent pair (constitution 8):
- **suppressed:** a repo with N pre-existing violations + a written baseline →
  `check --baseline` reports 0, exits 0.
- **new detected:** add one new violation → reported, exits 1; baselined ones
  stay suppressed.
- **edited re-triggers:** edit a baselined offending line → it resurfaces as new.
- **count:** 3 identical offending lines baselined, add a 4th → only the 4th is
  new.
- **`--changed` compose:** full-tree (cross-file) baselined violation stays
  suppressed under `--changed`.
- **stale:** fix a baselined violation → stale warning, exit unaffected.
- exit-code matrix: baselined-only → 0; any new error → 1; `--fail-on-warning`
  interaction.

No bench-compare threshold expected (suppression is O(violations), negligible vs
the walk); confirm the fingerprint's per-line file read doesn't regress the
hot path (it touches only files that already produced a violation).

## 7. Open questions

1. **Discovery / opt-in.** Explicit `--baseline <file>` only, or also a
   `baseline:` config key, or auto-detect `.alint-baseline.json` if present?
   Auto-detect is ergonomic but silently suppresses — risky as a default.
   *Leaning:* explicit flag **or** config key (both opt-in); no silent
   auto-detect. Resolve before implementation.
2. **Repo-level fingerprint.** Message-derived (simple, but reword-fragile) vs a
   structural key the rule supplies (stable, but needs a new per-rule hook).
   *Leaning:* message-derived for v1, with a normalisation pass; revisit if
   reword churn bites.
3. **Stale handling.** Warn-only (default) vs `--strict-baseline` to fail on
   stale (debt strictly non-increasing). *Leaning:* warn-only default + opt-in
   strict.
4. **`fix --only-baselined`** — a "pay down debt" mode that fixes only baselined
   violations. Useful, but scope-creep for v1; defer.
5. **Rename following.** Out of scope for v1 (path-keyed); note as a known churn
   source. Revisit if refactors prove painful.
6. **Hash truncation.** Full 32-byte SHA-256 hex vs a truncated (e.g. 8-byte)
   fingerprint for a smaller file. *Leaning:* truncate to 16 hex chars (8 bytes;
   collision-safe at repo violation counts) for readability, full hash internal.
7. **Version pinning.** Should the baseline record (and check) `alint_version` to
   warn when a rule-kind upgrade may have shifted fingerprints? *Leaning:*
   record as advisory provenance, don't hard-gate.
